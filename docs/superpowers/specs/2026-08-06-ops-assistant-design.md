# ops-assistant 运维助手设计文档

- 日期：2026-08-06
- 状态：已与需求方逐节确认，待实施
- 背景：生产环境（银河麒麟 V10、全离线内网）缺少 Python 运维工具及相关技术人员，值班人员无法自主排查故障。目标是利用内网已有的大模型网关，建设一套独立 Web 运维工具，覆盖**故障排查与诊断**、**日常巡检与健康检查**两类场景。

## 1. 需求与约束（已确认）

| 决策点 | 结论 |
|---|---|
| 核心场景 | ① 故障排查与诊断 ② 日常巡检与健康检查 |
| 大模型来源 | 复用现有内网 OpenAI 兼容网关（与主应用同一网关，可独立配置 key） |
| 工具形态 | 独立 Web 运维服务：独立进程、独立端口，主应用宕机时照常可用 |
| 操作权限 | **只读诊断 + 建议**：所有处置动作由人执行，工具不做任何写操作/修复动作 |
| 异常通知 | 仅页面展示（红黄绿状态 + 异常列表），不接外部通知通道 |
| 知识库维护 | runbook **页面可编辑**（存 ops 自己的 SQLite），离线包带出厂初始数据 |
| 审计粒度 | 诊断记录级留痕（谁、何时、诊断了什么、结论），不做全量操作日志 |

## 2. 方案选型

评估了三个方案，选定 **方案 C：规则巡检 + 预编排诊断流水线**：

- 方案 A（规则巡检 + LLM 只做解读）：稳定但诊断太浅，未知问题定位不到根因。
- 方案 B（LLM Agent 自主诊断循环）：灵活但不可控、token 消耗大、开发复杂度高。
- **方案 C**：巡检用纯规则引擎（零 LLM 依赖）；诊断走预编排采集流水线（固定路径）+ 单次 LLM 分析 + 可追问。诊断深度与可控性兼顾，成本可预测。

## 3. 总体架构与部署

```
┌─────────────────────────────────────────────────────┐
│                生产服务器（麒麟 V10 内网）              │
│                                                     │
│  ┌──────────────┐        ┌───────────────────────┐  │
│  │ 主应用 :8000  │◄─只读─│  ops-assistant :9100   │  │
│  │ (uvicorn)    │ 探测   │  ┌─────────────────┐  │  │
│  └──────────────┘        │  │ 巡检引擎(规则)    │  │  │
│  ┌──────────────┐        │  │ 诊断流水线(采集+LLM)│  │  │
│  │ MySQL/SQLite │◄─只读─│  │ 静态单页前端      │  │  │
│  └──────────────┘        │  └─────────────────┘  │  │
│  ┌──────────────┐        └──────────┬────────────┘  │
│  │ 日志文件目录  │◄─读取──────────────┘              │
│  └──────────────┘                   │               │
└─────────────────────────────────────┼───────────────┘
                                      ▼
                            内网 LLM 网关（复用现有）
```

关键决策：

1. **技术栈**：Python + FastAPI + Uvicorn，与主应用同栈；打包复用离线包已有的便携 Python 3.12 与 wheel 缓存，不引入新运行时依赖。前端为预构建静态单页（目标机无需 Node）。
2. **独立进程、独立端口（默认 :9100，可配）**，独立 pid 文件与日志，用主应用 `server.sh` 同款模式管理（start/stop/status）；可选纳入 nginx 反代（`/ops` 路径），也可直连端口。
3. **部署**：作为现有离线包新增子目录（`offline-bundle/ops/`），`start-offline.sh` 增加可选启动步骤；也支持单独 tar 包增量部署到已有环境。
4. **配置**：独立 `.env`（LLM 网关地址/key/模型、主应用安装路径、巡检间隔、端口等），默认值尽量从主应用 `.env` 自动推断。
5. **只读红线**：代码层面不引入任何针对主应用与系统的写操作——不删文件、不执行重启、数据库连接只读；所有输出均为建议，执行权在人。ops-assistant 只写自己的 SQLite 库。

## 4. 核心组件

### 4.1 采集器（collectors/）——只读数据探针

每个采集器为纯函数式探针，输出统一结构 `{status, summary, metrics, evidence}`，独立超时（默认 5s）：

| 采集器 | 采集内容 |
|---|---|
| `process` | 主应用 pid 文件、进程存活、`/health` 响应与耗时 |
| `logs` | `data/logs/app-*.log` 最近 N 小时（可配，默认 6 小时）ERROR/WARNING 计数、按关键模式聚类（LLM 超时、数据库连接失败、银行接口 5xx 等）、提取代表性错误片段（按 token 预算截断） |
| `system` | 数据/日志目录所在分区磁盘水位、内存、负载 |
| `database` | MySQL 连通性与 `SELECT 1` 耗时；或 SQLite 文件可读写性、体积 |
| `llm_gateway` | 网关可用性与最小 chat 调用延迟（每轮巡检/诊断只探测一次，避免白耗 token） |
| `bank_api` | 4 个银行营销接口连通性探测（优先低成本 GET） |

### 4.2 规则引擎（rules/）——巡检判定，零 LLM 依赖

- 规则 = 采集器结果 + 阈值/模式判定 → `绿/黄/红` + 一句话说明。
- **YAML 声明 + 少量 Python 判定函数**，新增规则不写框架代码。
- 内置首批规则（已确认不增删）：进程存活、health 超时、错误日志突增（对比昨日同时段）、磁盘 >85%、MySQL 不可达、LLM 网关延迟 >30s、银行接口失败。
- 执行：应用内 asyncio 后台定时循环（默认 30 分钟，可配；离线 wheel 无 APScheduler，故不引入新依赖）+ 页面手动"立即巡检"；结果存 ops 自己的 SQLite，保留 7 天滚动。

### 4.3 诊断流水线（diagnosis/）——预编排 + LLM 分析

固定流程，无自主循环，路径可预测：

```
值班人员点击某红/黄项的 [诊断]
  → ① 按检查项类型选择"采集剧本"（如 llm-latency 剧本 = logs + llm_gateway + 主应用模型配置）
  → ② 执行采集，组装结构化证据包（JSON + 截断后日志片段，控制在 token 预算内）
  → ③ 证据包 + 关联 runbook 注入提示词 → 单次 LLM 调用（超时 60s）
  → ④ 输出结构化结论：可能原因（按置信度排序）/ 建议操作（步骤化，附涉及的文件路径）/ 判断依据
  → ⑤ 值班人员可追问（多轮对话，证据包保留在上下文，工具集固定只读）
```

### 4.4 知识库（runbooks）——页面可编辑的故障手册

- 存储：ops SQLite 表（标题/分类/markdown 正文/更新时间），页面提供编辑器与预览。
- 出厂数据：从 `DEPLOY-OFFLINE-KYLIN.md`、`DEPLOY.md` 及历史排障记录提炼的首批 runbook（如 `llm-timeout`、`mysql-unreachable`、`disk-full`），首次启动时导入。
- 注入方式：按诊断剧本关联对应 runbook 直接拼入提示词，不做向量检索（内网无 embedding 服务，规模小不需要）。
- 知识沉淀闭环：诊断结论页提供 [存入知识库] 按钮 → 结论转为 runbook 草稿 → 编辑保存；下次同类问题自动注入。这是弥补"无 Python 运维人员"的关键机制。

### 4.5 前端（web/）——单页仪表盘

预构建静态页，三大区域：

1. **状态总览**：各检查项红黄绿卡片（灰色表示"未知/采集失败"）。
2. **巡检历史**：快照时间线。
3. **诊断面板**：点卡片发起诊断，展示结构化结论 + 追问对话 + [存入知识库]。

访问控制：简单访问令牌（内网 + 端口控制），不做复杂权限体系。

## 5. 数据流

### 5.1 定时巡检

asyncio 后台循环每 30 分钟触发 → 并行执行采集器 → 规则判定 → 快照写入 ops SQLite（7 天滚动）。
**页面打开时展示最近一次快照（秒开、不冲击主应用），点"立即巡检"才实时采集**——状态最多滞后一个巡检间隔，此取舍已确认。

### 5.2 诊断

见 4.3 流程。证据包组装时 LLM key、数据库口令等敏感信息一律脱敏。

### 5.3 知识沉淀

排障完成 → 诊断结论转 runbook 草稿 → 编辑保存 → 后续同类问题自动注入提示词。

### 5.4 存储小结

ops-assistant 仅有一个自己的 SQLite 库（巡检快照 + runbook + 诊断记录），位于 `ops/data/`，与主应用数据完全隔离。

## 6. 错误处理与降级

原则：运维工具存在的意义是主应用出问题时还能用，自身按故障域逐层降级。

| 故障 | 行为 |
|---|---|
| LLM 网关不可用 | 巡检照常（零 LLM 依赖）；诊断明确提示"LLM 暂不可用"，**降级展示规则判定原文 + 关联 runbook 全文**，值班人员可照手册处理 |
| 单个采集器失败 | 该采集器返回 `status=unknown` + 失败原因，其余照常；对应检查项显示灰色"未知"，不误报红 |
| 主应用完全宕机 | 主战场场景：process/health 报红，logs 采集器照常（日志文件仍在），诊断流水线正常出结论 |
| ops SQLite 损坏/磁盘满 | 巡检结果退化为只写日志文件，页面提示"历史不可用"，实时功能正常 |
| ops-assistant 自身宕机 | 与主应用相同的保活手段（systemd 或 crontab 兜底脚本）；日志按天轮转 |

防护细节：

- **token 预算硬上限**：单次诊断证据包超预算（默认可配，如 12k tokens）按"最新错误优先"截断，不让请求爆掉。
- **超时控制**：采集器各自超时（默认 5s），单轮巡检有总时长上限，避免单个探测卡死拖垮整轮。
- **密钥安全**：主应用配置进入证据包/页面前脱敏；ops 自己的 `.env` 同样脱敏显示。
- **审计**：诊断记录（谁、何时、诊断对象、结论）落库留痕。

## 7. 测试策略

遵循仓库现有 pytest 惯例，分四层：

1. **采集器单测**：fixture 构造假环境（假日志目录、假 pid 文件、mock HTTP 端点），重点覆盖边界：日志文件不存在、超大日志、MySQL 拒连、网关超时。
2. **规则引擎单测**：给定采集器结果断言红黄绿，每个内置规则至少正/反/边界三例。
3. **诊断流水线测试**：LLM 调用全部 mock（固定返回结构化结论），验证剧本选择、证据包组装、token 截断、runbook 注入；1-2 个提示词模板渲染契约测试。
4. **API 集成测试**：FastAPI TestClient 跑通关键端点（快照查询、立即巡检、发起诊断、runbook CRUD），外部依赖全部 mock。

不做（YAGNI）：端到端浏览器测试（前端简单，人工验证）；压测（值班人员个位数使用量级）。

## 8. 验收标准

1. 模拟"主应用进程被杀 + 日志有报错"：值班人员不读代码、只看 ops 页面，能在诊断结论指引下找到正确原因。
2. 模拟"LLM 网关不可用"：巡检照常出红黄绿，诊断降级展示规则判定 + runbook。
3. 全套测试在开发机离线可跑（无任何真实外部依赖）。
